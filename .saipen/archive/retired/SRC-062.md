[P1] [CORE-001] sailang/frame.py::Batch.parse + sailang/__init__.py exports + saimail/acceptance.py::receive
EVIDENCE: saimail/acceptance.py defines receive() as the receiver-owned route from raw wire to decoded views and requires ProfileRegistry acceptance before binding a profile. sailang/frame.py nevertheless exposes `Batch.parse(text, profile)`, which accepts an arbitrary caller-supplied Profile and directly creates bound frames. sailang/__init__.py publicly exports Batch, Profile, and decode, while Profile.inline remains publicly constructible. Existing `test_the_only_public_raw_wire_route_is_receive` inspects public functions in saimail.acceptance only and therefore misses this exported classmethod route. Reproduction created an unaccepted hostile inline profile remapping `QUEUE_OWNERSHIP_STALE`; `receive(wire, ProfileRegistry())` rejected it with PROFILE_NOT_ACCEPTED, but `Batch.parse(wire, hostile)` succeeded and `decode(...)` yielded the hostile profile's bound semantic claim.
DEFECT: the receiver-owned profile-acceptance invariant is not mechanically enforced. Raw external wire can bypass ProfileRegistry entirely whenever a caller uses the public sailang API directly. This reopens the exact trust class the acceptance layer is intended to close: arriving content or calling code can self-select its decoding dictionary and obtain apparently legitimate bound semantic frames.
REPAIR: make receiver acceptance a required capability for raw-wire binding rather than a convention. Remove or internalize the public `Batch.parse(text, Profile)` binding route, or require an opaque accepted-profile token/capability minted only by ProfileRegistry.resolve/receive. Producer-side Profile construction may remain public, but possession of a Profile alone must not authorize decoding untrusted external wire into TriageFrame/TriageView. Preserve the existing canonical frame/record ABI and avoid documentation-only enforcement.
VERIFY: add an exported-API regression that builds an unaccepted hostile Profile plus valid wire and proves every normal public route refuses to produce a bound/decodeable TriageView until the receiver registry accepts that profile. Explicitly cover `sailang.Batch`, package exports, and any compatibility parser retained after repair. Existing profile-acceptance, frame, record, and semantic ABI tests must remain green.

[P1] [CORE-004] saimail/quarantine.py::read_span
EVIDENCE: verify_derivative() checks the derivative body's recorded length/hash and correctly raises DERIVATIVE_CHANGED on tampering; represented_authority() invokes that verification. read_span(), however, performs only requested-span and redaction/offset checks before returning `(RESOLVED, derivative_bytes)` and does not authenticate the supplied derivative body. Its contract states that a RESOLVED result contains bytes that are the original's. Reproduction loaded an existing receipt derivative, changed its first bytes from the recorded content to `NOTMAIL` without updating its record, confirmed verify_derivative() rejected the body as DERIVATIVE_CHANGED, yet `read_span(record, forged_body, 0, 7)` returned `('RESOLVED', b'NOTMAIL')`.
DEFECT: read_span can certify tampered derivative data as RESOLVED/original bytes. Integrity verification is optional at exactly the API boundary that interprets bytes as authoritative source material, so a caller that reasonably relies on read_span's own contract can consume forged content.
REPAIR: require derivative integrity verification before read_span returns any RESOLVED bytes. The narrow repair is to invoke verify_derivative(record, derivative_body) before span resolution. If avoiding repeated hashing later becomes necessary, introduce a verified-derivative wrapper minted only by verify_derivative, but do not weaken the current digest/length invariant or make callers responsible through undocumented preconditions.
VERIFY: add a regression where a same-length derivative body is modified outside/inside the requested span and prove read_span fails with DERIVATIVE_CHANGED rather than returning RESOLVED data. Confirm pristine derivatives retain current RESOLVED/UNRESOLVED behavior and all quarantine/provenance tests remain green.

[P1] [W2-001] lab/saifren_run.py::Runner.call

[P1] [PERF-001] PROVEN BOTTLENECK sailang/frame.py::decode / TriageFrame.aliases / _decode_flags
EVIDENCE: every Batch.parse frame receives the same batch-local aliases tuple, but decode() executes `_decode_flags(flags, dict(frame.aliases))` for every frame. The dict conversion occurs before _decode_flags can take its immediate `flags == ABSENT` return, so even frames carrying no relation flags rebuild the entire alias table. Local receive() benchmarks using valid SAIB4 containers and an accepted Profile showed:
- N=1000,D=0: 0.0046 s median; N=1000,D=1000: 0.0255 s
- N=2000,D=0: 0.0090 s; N=2000,D=2000: 0.0961 s
- N=4000,D=0: 0.0197 s; N=4000,D=4000: 0.3867 s
- N=8000,D=0: 0.0419 s; N=8000,D=8000: 1.7360 s
With N and D growing together, the alias-bearing path trends O(N*D), effectively quadratic. cProfile at N=D=2000 placed 0.099 s of 0.107 s receive() cumulative time inside decode(), while parse itself consumed only ~0.006 s.
ISSUE: the batch pays alias indexing once logically but reconstructs it once per frame physically. A relation table intended to save wire space therefore creates a quadratic decode hot path as mailbox size and alias count rise. The waste is present even when every frame's flags slot is `-`.
OPTIMIZE: construct one alias lookup mapping per parsed Batch and share it across every bound frame, or otherwise provide decode() an immutable/shared alias lookup without rebuilding it. At minimum, do not construct any lookup when flags are ABSENT; however the final repair must also remove the O(N*D) worst case for relation-bearing frames rather than only optimizing the no-flags case.
GUARDRAIL: canonical SAIB4 bytes, alias identity, unresolved-alias behavior, relation_targets ordering and D-011/D-013 profile-binding semantics must remain byte/meaning compatible. Do not replace unresolved aliases with guesses and do not introduce mutable global alias state.
VERIFY: add a regression/instrumented test proving one N-frame batch builds the alias lookup O(1) times rather than N times. Add an alias-heavy scaling test comparing approximately N=D=1000 and N=D=4000 and require growth consistent with linear input processing rather than quadratic reconstruction. Retain all triage/profile acceptance tests and verify relation-bearing frames resolve exactly as before.

[P1] [PERF-002] PROVEN BOTTLENECK saimail/acceptance.py::receive + sailang/frame.py::Batch.parse
EVIDENCE: SAILANG batches have no implementation limit on raw container bytes, frame count, alias-definition count or per-frame line length. Batch.parse normalizes/splits the entire supplied string, builds a lines list, stores every alias tuple and creates every TriageFrame; receive() then materializes a second full tuple of TriageView objects. Synthetic accepted, valid batches demonstrated substantial amplification:
- Batch.parse, 10,000 frames / 150,092 input bytes: ~1.8 MiB tracemalloc peak
- 50,000 / 750,092 bytes: ~9.2 MiB
- 100,000 / 1,500,093 bytes: ~18.3 MiB
- 200,000 / 3,000,093 bytes: ~36.7 MiB
receive() amplified further:
- 10,000 / 150,092 bytes: ~5.5 MiB peak
- 50,000 / 750,092 bytes: ~27.6 MiB
- 100,000 / 1,500,093 bytes: ~55.3 MiB
No matching oversize/batch-bound regression exists in tests/test_triage_frame.py or tests/test_profile_acceptance.py. SENV1 already has explicit MAX_* bounds; the raw SAILANG receive surface does not.
ISSUE: external wire accepted under a legitimate profile can force memory and CPU proportional to an arbitrarily large N/D declaration and body. This is a stability/resource-exhaustion boundary, not merely a micro-optimization: a ~1.5 MiB legal batch produced ~55 MiB peak during receive(), and nothing prevents inputs much larger than that.
OPTIMIZE: define and enforce explicit protocol/receiver limits for batch bytes, frame count, definition count and individual line/frame length. Reject oversize input before full split/materialization whenever possible. Parse the header with a bounded first-line operation, validate declared N/D against limits before constructing frames, and avoid unnecessary whole-container normalization copies. Fail closed rather than truncate.
GUARDRAIL: limits must be documented as part of the receiving contract and chosen from declared mailbox/open-budget requirements, not tuned silently to the current benchmark corpus. Existing canonical batches below the limits must retain identical semantics. Oversize refusal must occur before decode/selection and must not partially return views.
VERIFY: add boundary tests at limit, limit+1 for bytes, N, D and line length; add a large rejected container test proving no tuple of frames/views is materialized before refusal. Include a memory regression or allocation proxy showing a rejected oversized batch does not scale peak allocations with its declared frame count. Existing normal Batch.parse/receive cases must remain green.

[P1] [PERF-003] PROVEN BOTTLENECK saimail/quarantine.py::scan
EVIDENCE: scan() decodes the complete body to text, then helper `at(char_index)` executes `len(text[:char_index].encode("utf-8"))` and `line_of(char_index)` executes `text.count("\n", 0, char_index) + 1` for each finding. Later matches therefore repeatedly rescan/re-encode increasingly large prefixes. Synthetic receipts containing repeated valid credential assignments showed superlinear runtime:
- 250 lines / 8,250 bytes: 0.00122 s
- 500 / 16,500: 0.00306 s
- 1,000 / 33,000: 0.00964 s
- 2,000 / 66,000: 0.0351 s
- 4,000 / 132,000: 0.119 s
- 8,000 / 264,000: 0.456-0.468 s
- 16,000 / 528,000: 1.84 s
- 24,000 / 792,000: 3.97 s
A 32x input increase from 250 to 8,000 lines increased median runtime by roughly 370x. There is no receipt-size bound in this module that prevents this path.
ISSUE: exact byte-offset and line-number reporting is implemented with repeated prefix work, turning a structurally linear scan into approximately quadratic behavior for bodies containing many findings. A sub-megabyte receipt can already consume several seconds locally, and build/check paths invoke scan synchronously.
OPTIMIZE: compute character-index -> UTF-8 byte-offset and line information in one forward pass, or scan bytes/text while maintaining running byte and line offsets. Every regex match should translate start/end positions in O(1) or amortized O(1), with total scan work approximately O(body + findings), not O(body * findings).
GUARDRAIL: preserve exact UTF-8 byte offsets, 1-based line numbers, finding categories, overlap deduplication and deterministic ordering. Non-ASCII fixtures are mandatory because replacing prefix encoding incorrectly can silently convert character offsets into byte offsets.
VERIFY: retain the existing UTF-8 offset determinism tests; add dense-finding ASCII and multibyte fixtures. Add a scaling regression where doubling a dense body does not approach 4x runtime/work, preferably using an instrumentable operation counter rather than a fragile wall-clock threshold. The current 24,000-line reproduction must complete without repeated prefix slicing/encoding.

[P1] [PERF-004] PROVEN BOTTLENECK saimail/quarantine.py::withheld_fragments + plaintext_leaks
EVIDENCE: withheld_fragments() tokenizes each redacted component and materializes every contiguous window of two or more alphanumeric runs (`for i ... for last in runs[i+1:]`), storing the resulting byte substrings in a set and finally sorting them. This creates O(R^2) patterns and O(R^3)-scale aggregate copied substring bytes for a component with R distinct runs. Synthetic single redactions produced:
- 80 runs / 479-byte component: 3,160 fragments, 527,720 total fragment bytes, ~0.79 MiB peak
- 120 runs / 719 bytes: 7,140 fragments, 1,763,580 bytes, ~2.53 MiB peak
- 200 runs / 1,199 bytes: 19,900 fragments, 8,099,300 bytes, ~10.9 MiB peak
- 300 runs / 1,799 bytes: 44,850 fragments, 27,223,950 bytes, ~30.1 MiB peak
- 400 runs / 2,399 bytes: 79,800 fragments, 64,398,600 bytes, ~69.8 MiB peak
- 500 runs / 2,999 bytes: 124,750 fragments, 125,623,250 bytes, ~129.7 MiB peak
plaintext_leaks() then compounds this by evaluating `data.lower()` inside the per-piece generator, recreating/lowering a complete candidate file for each fragment until a match is found. With only 545 pieces, one unmatched 500,000-byte file already required ~0.101 s locally.
ISSUE: a few-kilobyte withheld path/value can expand into hundreds of megabytes of fragment storage before archive leak checking even starts, and leak checking repeatedly copies each candidate file. This is a severe resource amplification in the subsystem specifically intended to make sensitive exports safer.
OPTIMIZE: replace exhaustive materialized substring enumeration with a bounded equivalent matcher. For leak existence, every longer contiguous multi-run window necessarily contains an adjacent two-run window, so a minimal sufficient search basis can use adjacent run-pairs plus qualifying long single runs, preserving separator bytes; alternatively implement a streaming/multi-pattern matcher without materializing all O(R^2) substrings. Lower each candidate file exactly once. If compatibility requires withheld_fragments() to remain public, keep its contract bounded or route safety-critical plaintext_leaks() through the compact matcher rather than the expansion API.
GUARDRAIL: do not weaken leak detection for a copied complete component, any contiguous multi-run subcomponent, or a qualifying long single run. Preserve extension exclusion behavior and case-insensitive matching. Optimization must never print, persist or expose withheld bytes.
VERIFY: add equivalence tests comparing old exhaustive semantics against the optimized matcher over generated components/files before deleting the reference implementation. Include a 500-run synthetic component and assert bounded fragment/matcher state rather than ~124,750 materialized substrings. Add multi-megabyte unmatched-file coverage proving each file is normalized/lowered once, not once per secret fragment.

[P2] [PERF-005] LOW-RISK SIMPLIFICATION sailang/frame.py::Profile.id
EVIDENCE: Profile.id is a property that reconstructs descriptor bytes and computes SHA-256 on every access even though frame_version, dictionary_version and dictionary_digest defining the identity are immutable for the lifetime of the Profile. Every decoded frame writes `profile_id=frame.profile.id`. cProfile of an alias-free 20,000-frame receive recorded 20,001 Profile.id calls with ~0.037 s cumulative time, including 20,001 descriptor constructions, UTF-8 encodes and SHA-256 operations. The same immutable identity is therefore cryptographically recomputed once per message.
ISSUE: profile identity is batch-scoped by D-011 but CPU work is still paid per frame. On an otherwise simple alias-free batch this represented a visible fraction of decode time and adds needless hashing/allocation to the hottest normal path.
OPTIMIZE: calculate the profile id once at Profile construction or lazily cache it once per Profile instance. Batch.parse/receive/decode should reuse that immutable value.
GUARDRAIL: the cached value must remain exactly `sha256(descriptor())` and must not become a mutable/global "current profile". Profile equality, dictionary digest binding and historical frame identity must remain unchanged.
VERIFY: add a deterministic identity test comparing the cached id with the current descriptor hash for loaded and inline profiles. Instrument a many-frame receive and prove SHA-256 identity computation occurs O(1) times per Profile/batch rather than once per frame. Retain all profile mismatch and historical-version tests.
