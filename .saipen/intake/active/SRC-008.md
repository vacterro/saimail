TARGET A — MAKE THE CREDENTIAL RESOLVER THE CANONICAL PATH
======================================================================

GOAL

The human provisions the SAIRoute credential once.

Future agents use the named local credential handle.

They do not need the human to paste the key again.

Canonical handle:

credential://9router/sairoute

--------------------------------------------------
A1 — CREDENTIAL MANAGER FIRST
--------------------------------------------------

Current `lab/saifren_run.py` still reads:

SAIROUTE_API_KEY

in `main()` before the resolver is called.

This means an inherited environment variable silently bypasses the persistent
credential-store path.

Change the ordinary live command so the canonical path is:

SAIRoute logical credential handle
-> local credential resolver
-> Windows Credential Manager
-> transport

The default CLI must not require or prefer a secret environment variable.

If environment-variable compatibility is retained, make it an EXPLICIT
legacy/debug mode rather than an invisible precedence rule.

Do not remove compatibility merely for aesthetics if an existing workflow
depends on it; make the authority/precedence explicit.

--------------------------------------------------
A2 — INTERACTIVE PROVISIONING ONLY
--------------------------------------------------

Current provisioning code uses getpass on a TTY but falls back to:

stdin.readline()

when stdin is not a TTY.

Remove the normal non-TTY secret ingestion path.

The ordinary provisioning tool must require a real interactive non-echoing
prompt.

Reason:

echo SECRET | provision.py

can put the secret into shell history and defeats the purpose of the resolver.

Fail cleanly when no TTY is available.

Tests may inject a fake backend and mock getpass directly.

Do not create:
--key SECRET
--secret SECRET

or another command-line secret surface.

--------------------------------------------------
A3 — BACKEND CLAIMS
--------------------------------------------------

The implementation currently says "Windows Credential Manager via keyring".

Verify what guarantee is actually made by the code.

Do not claim a specific backend merely because `keyring` is imported.

If the runtime is Windows and the selected backend is not suitable for the
declared persistent local store, report a clear operational error.

Do not create a large backend abstraction.

--------------------------------------------------
A4 — DOCUMENTATION
--------------------------------------------------

Update the lab module documentation and README.

They currently still describe the credential as environment-only.

Document:

one-time provisioning command
check command
rotation/replacement
deletion
normal live command

Never print or document a real credential value.

--------------------------------------------------
A ACCEPTANCE
--------------------------------------------------

- ordinary live execution resolves the named credential without environment
  secret injection

- tests never touch the real store

- README and code describe the same path
