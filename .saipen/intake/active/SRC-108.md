## Request

SAITELEMES RELIABLE AUTONOMOUS DELIVERY v1

Сейчас новый snapshot уже после вчерашнего blocker: T-116 DONE, T-117 DONE, STATE = DONE, task = none. В T-117 реализован тот самый следующий brick, о котором мы раньше говорили: SAIPEN на continue/status автоматически видит входящие SAITELEMES, но только header metadata. Private keys при этом больше вообще не вытаскиваются из credential store. Канонический suite: 2567 passed, причём финальный прогон зелёный.

Что мы уже заложили в SAIMAIL за прошлые этапы: offline SENV2 transport, authenticated sender/receiver, persistent workspaces, dedup, explicit Open/Reopen, ciphertext-only private storage, HUMAN_PRIVATE, receiver-owned attention budget RESERVE → ACK_PRESENTED, crash recovery, SAITELEMES, SAIPEN Seam, Work Desk, bounded pagination/context hashes, inert command-looking text, project/seat admission и теперь secret-free automatic turn-entry awareness. То есть foundation уже нихуя не игрушечный.

Теперь важная часть: что добавлять дальше, чтобы он стал не просто technically correct, а operationally dependable. Абсолютного «работает точно всегда» в software не существует, это человеческая разновидность единорога. Но можно добиться свойства: crash, retry, duplicate, stale state, wrong seat и временная недоступность не приводят к потере или неправильному действию.

Я бы строил дальше вот так, именно в таком порядке:

Сначала закрыть три SAIPEN-side дефекта, найденные T-117. Это сейчас P0 для integration quality. SAIPEN должен читать refusal из status, а не несуществующего code; read_command должен возвращать copy-safe argv/корректно quoted paths; turn-entry обязан сравнивать workspace.seat с acting seat и при mismatch показывать отдельное состояние, а не чужие counts. Это небольшая работа, но она превращает integration из «работает в happy path» в контрактно правильную.
Automatic SAITELEMES sender trigger. Это как раз вторая половина нашей старой идеи. Сейчас receiving автоматический, sending ещё manual. SAIPEN должен автоматически создавать telegram только на строго определённых событиях: найден cross-agent blocker, finding относится к Work другого агента, dependency стала actionable, ownership изменился, запрошен handoff. Никакого «LLM решил поболтать». Event-driven policy, closed set триггеров.
Durable Outbox + idempotency. Это, пожалуй, самый важный следующий architectural brick. Сначала durable intent записывается на диск, потом message seal/delivery, потом delivery receipt. Каждый автоматический telegram получает deterministic IDEMPOTENCY_KEY, например от project/work/event/recipient. После crash система повторяет доставку, но receiver dedup превращает повтор в no-op. Не надо обещать магическое exactly-once delivery. Нормальная distributed semantics: at-least-once transport + exactly-once observable effect через idempotency. Вот это уже взрослый engineering.
Project-local Agent Registry. Раньше мы специально запретили global discovery registry, и правильно. Но automation нужно знать, куда слать. Значит нужен explicit local mapping: project → participating seats → mailbox/workspace → accepted identity → capabilities. Не «нашёл какого-то агента в системе и послал ему хрень», а заранее admitted participant. Receiver-owned trust остаётся неприкосновенным.
S4 registered SAIPEN extension. В roadmap это как раз ещё NOT STARTED. Вместо набора loose CLI calls SAIMAIL становится formally registered capability SAIPEN. На entry проводится capability negotiation: schema version, API version, mailbox, seat, workspace health, secret-free header capability. Несовместимость должна давать DEGRADED, а не ломать весь saipen continue. Это идеально совпадает с твоим принципом fail-open degraded: если SAIPEN способен работать без почты, он работает и честно пишет, что telegram channel unavailable.
Agent acknowledgement protocol. Не путать с Open/Read. Нужны разные факты: DELIVERED означает envelope оказался у receiver; OBSERVED_HEADER означает агент увидел metadata; OPENED только после explicit decrypt; ACTED вообще нельзя автоматически выводить из message state. Это убирает мерзкую человеческую привычку считать «две галочки = понял и сделал».
Agent backpressure / flood control. Human Attention Budget у нас уже есть, но automatic agent-to-agent traffic создаёт новый ресурс: agent attention. Нужны per-project/per-sender/per-topic limits, duplicate collapse, bounded pending queue и deterministic overflow policy. Sender всё ещё не имеет права поставить себе URGENT=999, потому что иначе каждый агент мгновенно объявит себя центром вселенной. Eesti keeles: saatja ei otsusta vastuvõtja prioriteeti, отправитель не определяет приоритет получателя.
Crash matrix и concurrency torture. Убивать процесс после каждого durable transition: intent written, before seal, after seal, before delivery, after delivery, before ACK, after ACK. Затем restart и проверять invariants. Параллельно 2, 4, 8, 12 agents, поскольку твоя реальная цель именно multi-agent operation. Нужны tests на simultaneous writers, stale locks, abandoned leases, duplicated retries и mailbox rotation. 日本語で言えば 壊れても戻れる (даже сломавшись, способен восстановиться, kowarete mo modoreru). Вот это важнее красивого GUI в десять раз.
Health + telemetry без утечки payload. Один saimail-local health/status должен показывать: configured seat, peer count, pending outbox, unread header count, retry count, oldest pending age, last successful delivery, last error class, API compatibility, degraded capabilities. Никакого plaintext. Тогда агент может сам понять «почта работает / канал временно мёртв / неправильный seat», а не гадать по звёздам и traceback.
Только после этого external adapters / SAIRELAY. Это та более дальняя идея, которую мы обсуждали: SAIMAIL становится headless communication-intelligence layer, над которым adapters для Gmail/Slack/Outlook/других каналов, contact memory, policies, deduplication, action queue и audit trail. Но я бы сейчас туда не лез. Сначала доказать автономный local agent mesh. Потом transport adapters становятся всего лишь ingress/egress, а не новой архитектурой.

Если свести всё к одному target architecture, она выглядит так:

SAIPEN event → policy gate → durable outbox → authenticated SAITELEMES → recipient dedup → bounded header awareness → explicit open/action → receipt → audit

И на каждом переходе есть durable evidence, idempotency и recovery.

Самый правильный следующий wave прямо сейчас я бы определил как:

SAITELEMES RELIABLE AUTONOMOUS DELIVERY v1

В него входят только пункты 1–5: исправить SAIPEN consumer defects → automatic sender trigger → durable outbox/idempotency → explicit participant routing → S4 registration/capability negotiation.

После этого впервые можно будет практически сказать:

агент A во время работы обнаружил информацию для агента B, система сама надёжно передала её B, B автоматически увидел наличие сообщения на следующем turn, crash/restart ничего не потерял, duplicate ничего не сделал дважды, неправильный seat ничего чужого не увидел, private keys для awareness не потребовались, а само сообщение не получило никакой власти над SAIPEN.

Вот это уже будет реально работающая нервная система агентов, а не просто excellent collection of individually correct primitives.

Условный КПД я бы оценил сейчас так: primitives/security около 90%, SAIPEN receive integration 85–90%, autonomous agent-to-agent loop пока примерно 55–60%, потому что receive уже автоматический, а reliable automatic send + routing + durable acknowledgement ещё отсутствуют. После wave выше practical autonomy прыгнет примерно к 80–85%. Последние проценты съедят soak/concurrency/failure injection, как обычно. Software любит брать ипотеку именно на последние десять процентов.
