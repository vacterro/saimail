EXTERNAL TECHNICAL BASELINE
======================================================================

The implementation may target YubiKey PIV through Yubico's supported Python stack.

The relevant hardware capability is:

PIV private EC key
+
P-256 ECDH key agreement
+
optional PIN policy
+
optional touch policy

A PIV private-key operation may require PIN verification and hardware touch
according to the key's immutable generation/import policy.

YubiKey PIV supports key agreement using an EC private key in a PIV slot.

Do not reinterpret this as:

FIDO2 encryption

or:

private-key operation under its configured policy.

----------------------------------------------------------------------
A1 — THREE DISTINCT CONCEPTS REMAIN DISTINCT
----------------------------------------------------------------------

=

PRIVATE_KEY_CUSTODY
=

LOCAL_INTERACTION_POLICY
=
whether the device requires PIN and/or touch before ECDH

Do not collapse these into one concept called "authentication".

----------------------------------------------------------------------
A2 — HARDWARE-BACKED MEANING
----------------------------------------------------------------------

For SAIMAIL v0, HARDWARE_BACKED means:

- the recipient P-256 private key is held by a supported hardware token
- SAIMAIL receives only the public key and ECDH result
- SAIMAIL does not request/export raw private-key material
- ECDH is performed by the token/provider

It does NOT mean:

- the OS cannot observe decrypted plaintext
- malware cannot invoke the provider
- the sender knows which person touched the device
- the token proves subjective human intent
- the entire application is hardware-isolated

----------------------------------------------------------------------
A3 — PRESENCE TERMINOLOGY
----------------------------------------------------------------------

Do not call PIV touch:

HUMAN_IDENTITY_PROOF

Use a narrower term such as:

LOCAL_INTERACTION_REQUIRED

or:

HARDWARE_TOUCH_REQUIRED

A configured touch policy establishes that the physical device demanded a touch
for the key operation.

It does not identify the person who touched it.

PIN policy establishes successful knowledge-factor verification according to the
device/session policy.

Keep these claims exact.

----------------------------------------------------------------------
A4 — REFERENCE HARDWARE PATH
----------------------------------------------------------------------

Reference implementation:

PIV

specific SAILETTER key.

----------------------------------------------------------------------
A5 — REQUIRED POLICY FOR FUTURE SAILETTER HARDWARE KEY
----------------------------------------------------------------------

The future provisioned reference profile should require:

KEY_TYPE = ECCP256

PIN_POLICY =
ONCE or ALWAYS

TOUCH_POLICY =
ALWAYS

TOUCH_POLICY = ALWAYS

Rationale:

- PIN proves possession of the knowledge factor for the active token session
- touch requires a physical interaction for every private-key operation
- the UX remains tolerable while each decrypt operation still requires touch

Do not silently accept:

or:

TOUCH_POLICY = NEVER

as satisfying the future hardened profile.

A pre-existing key with weaker policy may be reported as:
