--------------------------------------------------
B1 — EXACT CIPHERTEXT HASH SEMANTICS
--------------------------------------------------

Resolve the current ambiguity around:

HASH: sha256(payload bytes)

For SENV1 define the clear-header hash as a hash of the EXACT SEALED CIPHERTEXT
BYTES.

Conceptually:

CIPHER_HASH = SHA256(ciphertext_bytes)

This allows the receiver to authenticate the encrypted body before decrypting.

Normal verification order:

1. parse bounded clear header
2. obtain exact ciphertext bytes
3. compute and compare CIPHER_HASH
4. resolve accepted sender verification key
5. verify Ed25519 signature
6. resolve recipient decryption key
7. decrypt
8. parse payload as inert data

No plaintext parsing occurs before steps 1-7 complete.

If a plaintext content hash is useful, keep it inside the encrypted payload or
define it separately.

Do not overload CIPHER_HASH with both meanings.

--------------------------------------------------
B2 — EXACT SIGNATURE DOMAIN
--------------------------------------------------

Define canonical bytes for the signature.

At minimum specify:

- exact field order
- UTF-8
- LF
- no BOM
- duplicate-field rejection
- unknown-field handling
- whitespace behavior
- which fields are included
- SIG excluded from its own signature
- ciphertext hash included
- final newline behavior

There must be exactly one byte representation for one signed header.

Do not rely on dict ordering or parser normalization.

--------------------------------------------------
B3 — KEY IDENTITIES
--------------------------------------------------

Seat identity and cryptographic key identity are separate.

Header must bind sender and recipient to exact key identities.

Conceptually:

FROM:<seat>
FROM_KID:<fingerprint>

TO:<seat>
TO_KID:<fingerprint>

Use a deterministic full public-key fingerprint.

Do not use a short display prefix as authority.
